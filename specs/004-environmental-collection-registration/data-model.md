# Data Model: Registro geral de coleta ambiental

**Feature**: IMP-004

**Date**: 2026-09-15

Este é o modelo-alvo do planejamento, não uma migration executada. Depende integralmente do modelo planejado pela IMP-003. Campos e relações científicas existentes são preservados como legado técnico, sem autoridade científica nem exposição nesta feature.

## Relationship Overview

```text
User 1 ─────────────── * CollectionData * ─────────────── 1 LaboratoryRoom
                              │                                  │
                              └──────── * : 1 CollectionArea ────┘

CollectionData(collectionAreaId, laboratoryRoomId)
  → CollectionArea(id, laboratoryRoomId)

CollectionData confirmed by IMP-004
  = occurredAt + occurrenceOffset + confirmedAt + confirmationKey all present
```

Cada coleta pertence diretamente a um laboratório e a uma área desse mesmo laboratório. A autoria aponta para o principal autenticado. A chave composta impede associação área–laboratório forjada mesmo fora do serviço.

## Entity: CollectionData

Evolução lógica planejada do model existente:

```prisma
model CollectionData {
  id               String   @id @default(uuid())
  createdAt        DateTime @default(now())
  updatedAt        DateTime @updatedAt
  collectionAreaId String
  laboratoryRoomId String
  userId           String
  observations     String?

  occurredAt      DateTime? @db.Timestamptz(3)
  occurrenceOffset String?  @db.VarChar(6)
  confirmedAt     DateTime? @db.Timestamptz(3)
  confirmationKey String?

  user           User           @relation(fields: [userId], references: [id], onDelete: Restrict)
  laboratoryRoom LaboratoryRoom @relation(fields: [laboratoryRoomId], references: [id], onDelete: Restrict)
  collectionArea CollectionArea @relation(
    fields: [collectionAreaId, laboratoryRoomId],
    references: [id, laboratoryRoomId],
    onDelete: Restrict
  )

  // Relações legadas preservadas e não consumidas pela IMP-004:
  waterData      WaterData[]
  soilData       SoilData[]
  vegetationData VegetationData[]
  terrainData    TerrainData[]
  diagnoses      IHFRDiagnosis[]

  @@unique([userId, confirmationKey])
  @@index([collectionAreaId, laboratoryRoomId])
}
```

`confirmedAt` não recebe default físico. O serviço o define automaticamente com o relógio autoritativo dentro da mesma transação que valida o contexto e cria a coleta. Assim, escritores legados que desconhecem os campos aditivos continuam produzindo a tupla toda nula, enquanto o fluxo IMP-004 fornece a tupla toda preenchida.

| Field | Type | New IMP-004 record | Origin and rule | Public |
|---|---|---:|---|---:|
| `id` | UUID represented as string | required | Existing opaque identifier; generated by the system | yes |
| `createdAt` | legacy `timestamp(3)` | generated | Technical creation timestamp; not occurrence or confirmation | no |
| `updatedAt` | legacy `timestamp(3)` | generated | Technical compatibility field; no public update exists | no |
| `collectionAreaId` | string | required | Derived from contextual route and revalidated area | only through area reference |
| `laboratoryRoomId` | string | required | Derived from contextual route; must match the area's laboratory | only through laboratory reference |
| `userId` | string | required | Derived exclusively from authenticated principal | no |
| `observations` | nullable string | unused | Existing legacy field; not accepted or exposed | no |
| `occurredAt` | `timestamptz(3)` | required | Instant parsed from RFC 3339 and normalized | yes, reconstructed with stored offset |
| `occurrenceOffset` | `varchar(6)` | required | Canonical submitted `Z` or `±HH:MM`; `-00:00` forbidden | yes, within `occurredAt` serialization |
| `confirmedAt` | `timestamptz(3)` | required | Generated automatically by the service during the insert transaction | yes, UTC `Z` |
| `confirmationKey` | UUID string | required | Internal idempotency key from required header, scoped by author | no |

Physical nullability of the four confirmation-tuple fields exists only for legacy compatibility. Application types for creating or returning an IMP-004 collection treat them as non-null.

## Parent Model Additions

The IMP-003 target `CollectionArea` receives the composite candidate key required by the tenant-safe foreign key:

```prisma
model CollectionArea {
  id               String @id @default(uuid())
  laboratoryRoomId String
  // fields and relations owned by IMP-003 remain unchanged

  collectionData CollectionData[]

  @@unique([id, laboratoryRoomId])
}
```

`LaboratoryRoom` exposes the inverse internal relation `collectionData CollectionData[]`. These additions do not modify its public DTO or the immutable area–laboratory association.

## Database Invariants

1. `id` is generated by the system and remains the public opaque collection identifier.
2. `(collectionAreaId, laboratoryRoomId)` must reference the same pair in `CollectionArea`; both foreign keys use `ON DELETE RESTRICT`.
3. `userId` must reference an existing author and remains unchanged after confirmation.
4. `(userId, confirmationKey)` is unique when the key is present.
5. `occurredAt`, `occurrenceOffset`, `confirmedAt` and `confirmationKey` are either all null (legacy) or all non-null (IMP-004 confirmed).
6. `occurrenceOffset` must be canonical `Z` or a real numeric offset between `-14:00` and `+14:00`; `-00:00` is invalid.
7. `occurredAt` cannot be enforced as “not future” by a stable database check; the service validates it against the authoritative injected clock inside the transaction.
8. A trigger rejects `UPDATE` and `DELETE` when the existing row has non-null `confirmedAt`.
9. No constraint, field or relation added by IMP-004 defines water, soil, vegetation, terrain, IHFR or another scientific measurement.

## Temporal Value Object

### Input profile

`occurredAt` is a canonical RFC 3339 timestamp:

```text
YYYY-MM-DDTHH:mm:ss[.S{1,3}](Z|±HH:MM)
```

Rules:

- Gregorian date and clock components must form a real civil timestamp.
- Offset is mandatory; local time without offset is rejected.
- `Z` means explicit UTC; `-00:00` is rejected as unknown local offset.
- Offset must be a currently representable whole-minute offset from `-14:00` to `+14:00`.
- Seconds `60` and more than three fractional digits are rejected instead of normalized.
- After parsing, `occurredAt` may equal but cannot exceed the current server instant.

### Storage and output

- `occurredAt` stores the UTC-normalized instant with millisecond precision.
- `occurrenceOffset` stores the canonical offset from input.
- The public `occurredAt` is reconstructed from both fields, preserving the same instant and registered offset.
- `confirmedAt` is generated independently and serialized in UTC with `Z` and millisecond precision.
- No display path may substitute browser/server timezone for the stored offset.

An offset disambiguates the occurrence instant even during daylight-saving folds. IANA rules, unknown or imprecise time and future scheduling are outside this feature.

## Idempotency Identity

`Idempotency-Key` identifies one confirmation action, not one combination of business values.

Canonical tuple compared on replay:

```text
userId + confirmationKey
  ↳ laboratoryRoomId + collectionAreaId + occurredAt instant + occurrenceOffset
```

- Same key and same tuple: return the existing collection and do not write.
- Same key and different contextual/temporal tuple: `409 CONFLICT`.
- Different keys and equal business values: create distinct collections.
- Authorization is revalidated before returning an idempotent replay.

No request fingerprint or generic idempotency table is required because all accepted inputs are stored and can be compared directly.

## State Transitions

```text
EDITING (client memory only)
  ├─ validate error ───────────────> EDITING
  └─ valid review ────────────────> REVIEWING (client memory only)
                                      ├─ back/correct ─> EDITING
                                      └─ confirm ──────> SUBMITTING
                                                            ├─ failure/retry ─> SUBMITTING with same key
                                                            └─ success ───────> CONFIRMED (persisted, immutable)

CONFIRMED ── GET detail ──> CONFIRMED
```

There is no persisted draft, update or deletion transition. A new intentional collection starts a new volatile flow and new confirmation key; it never mutates a confirmed row.

## Public Projections

```ts
type CollectionDetailDto = {
  id: string;
  occurredAt: string;  // RFC 3339 reconstructed with registered offset
  confirmedAt: string; // RFC 3339 UTC (Z)
  area: {
    id: string;
    name: string;
  };
  laboratory: {
    id: string;
    name: string;
    status: "ACTIVE" | "INACTIVE";
  };
  readOnly: boolean;
};
```

The DTO never includes `userId`, author identity, membership role, access code, `confirmationKey`, `createdAt`, `updatedAt`, `observations`, measurement groups or diagnoses.

## Contextual Query Rules

- Create: authorize laboratory with `CREATE_COLLECTION`, then resolve area by `(areaId, laboratoryId)` in the same transaction.
- Detail: authorize contextual read, then resolve a confirmed IMP-004 row by `(collectionId, collectionAreaId, laboratoryRoomId)` and `confirmedAt IS NOT NULL`.
- Replay: authorize again, find by `(userId, confirmationKey)`, then verify the complete canonical tuple before returning.
- A valid identifier in another laboratory/area is indistinguishable from a nonexistent identifier.
- Inactive laboratory permits detail with `readOnly: true`, but creation returns `409 READ_ONLY`.

## Migration Strategy

### Mandatory predecessor gate

Before generating or applying IMP-004 DDL, confirm the implemented schema matches the IMP-003 target: contextual roles, opaque area ID, direct area–laboratory association and guard contract are integrated and tested. The current baseline does not satisfy this gate.

### Preflight

1. Reconcile migration history and detect drift in an isolated target.
2. Count `CollectionData` and each scientific child without exposing record contents.
3. Verify every `CollectionData.collectionAreaId` resolves to exactly one area and laboratory.
4. Detect orphaned users, areas or laboratories and any area–laboratory inconsistency.
5. Confirm the IMP-003 uniqueness/constraints needed for the composite reference.
6. Abort before writes if deterministic `laboratoryRoomId` backfill is impossible.

### Forward migration

1. Add `laboratoryRoomId`, `occurredAt`, `occurrenceOffset`, `confirmedAt` and `confirmationKey` as nullable, without temporal defaults.
2. Backfill only `laboratoryRoomId` from the area relation and verify counts.
3. Make `laboratoryRoomId` non-null after proof; add inverse relation in the Prisma model.
4. Add unique parent `(CollectionArea.id, laboratoryRoomId)` and compound child FK with `RESTRICT`.
5. Add unique `(userId, confirmationKey)`, contextual child index and confirmation-tuple/offset checks.
6. Keep `confirmedAt` without a physical default so legacy writers preserve the all-null tuple.
7. Add the immutable-row trigger for rows whose `confirmedAt` is non-null.
8. Recheck counts, relations, constraints and unchanged scientific children before commit.

No column, relation, enum or row is removed or scientifically reclassified.

### Recovery and rollback

- A failure within the transactional DDL rolls back the migration.
- Old application code can ignore additive columns during rollback.
- After new confirmed collections exist, never drop the columns automatically; deploy a forward-fix or restore a previously tested snapshot/PITR if rollback is unavoidable.
- Migration tests cover empty and legacy-populated databases, scientific children, failure before commit, concurrency and restoration instructions.

## Legacy Scientific Models

`IHFRDiagnosis`, `WaterData`, `SoilData`, `VegetationData` and `TerrainData` remain physically related to `CollectionData`. IMP-004 does not include them in queries, inputs, outputs, fixtures of the primary journey or acceptance assertions. Their presence is `EVIDENCIA_IMPLEMENTACAO`, not an approved contract. Any future scientific feature must obtain authority and plan its own evolution.
